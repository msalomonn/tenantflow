# TF-04 acceptance hardening — 2026-11-05

Scope: T011 / issue #5, after TF-02 and TF-03 integration. Complete acceptance-to-test mapping and enforce repeatable CI/dependency analysis. This delivery does not deploy the app or claim production readiness.

- H01: map TF-A01–A09 to reproducible existing/new integration and browser checks, including negative cases and explicit limits. Add tests for uncovered security boundaries rather than duplicating all implementation details.
- H02: an absent, forged, expired or revoked session cannot access protected organization/project/member operations. Wrong-password sign-in must not establish a session. A session lost during a project mutation returns the browser to login with prior data/forms removed. Headers cannot forge user or tenant authorization.
- H03: retain exact-origin checks for POST/PATCH/DELETE, restricted runtime role validation and production HTTPS/secret requirements. Test production cookie attributes in a local HTTP harness configured for an HTTPS origin; do not equate those assertions with a deployed TLS/proxy test. Project names remain inert text, and invalid UI drafts are rejected accessibly before mutation.
- H04: CI starts from checkout + npm ci, generates local credentials without overwriting them on repeat setup, starts an isolated ephemeral database, applies migrations twice, builds/types/tests and runs dependency analysis. Any reported npm advisory fails the dependency check, including development dependencies. Registry/service failure must fail, not silently skip. Version pins/lockfile remain unchanged unless a reviewed finding requires an update.
- H05: record the audit date, command, lockfile fingerprint, findings and limitations; map local and CI evidence separately. Keep screenshots synthetic. Production deployment, hosting/costs, email delivery, public quotas, retention, licensing/profile presentation and deployed smoke remain TF-05/release work. An advisory database with no findings is not a security certification.
